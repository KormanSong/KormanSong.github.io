FreeRTOS 태스크는 기능별로 나누지 않고, 각 태스크가 무엇을 기다리는지에 따라 나눈다. 버튼 두 개로 동작하는 작은 카운터를 만들면서 정한 기준이다.

## 문제

과제는 7세그먼트 표시기에 숫자를 세어 보여 주는 카운터였다. 사양은 다음과 같다.

- A 버튼을 누르면 1초마다 1씩 세기 시작한다. A를 다시 누르면 일시 정지하고, 한 번 더 누르면 이어서 센다.
- B 버튼은 언제든 카운트를 0으로 만든다.
- 일시 정지 중에 B를 누르면 0을 표시하고 정지 상태를 유지한다. 세는 중에 B를 누르면 0부터 다시 센다.

처음에는 태스크 두 개로 구성했다. 표시 태스크는 공유 변수 값을 표시했고, 카운터 태스크는 1초마다 그 값에 1을 더했다. 여기까지는 문제없이 동작했다.

B 버튼 처리에서 막혔다. B는 상황마다 하는 일이 다른 것처럼 보여서 어느 함수에서 처리해야 할지 정하지 못했다. MCU 펌웨어를 2년 동안 개발했지만 처음에는 답이 보이지 않았다.

## 원인

장치를 입력이 들어가면 출력이 나오는 함수로 보고 있었다. 내가 맡은 MFC 펌웨어가 이 구조로 동작한다. 제어 루프가 ADC 값을 읽어 연산한 뒤 DAC로 출력한다.

카운터는 다르다. 같은 입력(B)이라도 앞서 어떤 일이 있었는지에 따라 결과가 달라진다. 디지털 회로로 보면 카운터는 순차 회로이고, 함수는 조합 회로다. 함수는 이전 상태를 기억하지 못하므로 카운터를 표현할 수 없다.

상태라는 개념이 빠져 있었다. 상태를 넣어 장치의 동작을 식으로 나타내면 다음과 같다.

> 출력 = f(입력, 상태), 다음 상태 = g(입력, 상태)

상태는 RUN과 PAUSE 두 가지, 이벤트는 A, B, TICK 세 가지다. 상태 전이표는 다음과 같다.

| 상태 \ 이벤트 | A | B | TICK |
|---|---|---|---|
| RUN | PAUSE로 전이 | count = 0 | count++ |
| PAUSE | RUN으로 전이 | count = 0 | (무시) |

표로 정리하면 B는 단순하다. 두 상태 모두에서 B는 카운트를 0으로 만들 뿐 상태는 바꾸지 않는다. RUN 상태에서는 TICK을 계속 처리하므로 0부터 다시 세게 되며, B가 따로 하는 일은 없다.

## 분리 기준

처음에는 표시, 카운터, 버튼처럼 기능마다 태스크를 하나씩 두려고 했다. 이 기준이 틀렸다.

FreeRTOS 태스크는 스택이 따로 있는 실행 단위이고, 블록 상태에서 CPU를 쓰지 않고 기다릴 수 있다. 아무것도 기다리지 않는 작업은 태스크로 만들 필요 없이 함수로 호출하면 된다. 지금은 기다리는 대상을 기준으로 태스크를 나눈다.

- 같은 주기로, 정해진 순서대로 실행하는 작업은 한 태스크에 넣는다.
- 주기가 다르거나 기다리는 이벤트가 다른 작업은 태스크를 따로 둔다.
- 주변장치는 분리 기준으로 삼지 않는다. 주변장치는 필요로 하는 태스크가 쓴다.
- 인터럽트 서비스 루틴(ISR)은 이벤트를 큐에 넣고 바로 복귀한다.

태스크는 여전히 두 개다. 로직 태스크는 이벤트를, 표시 태스크는 2ms 주기를 기다린다. 기다리는 대상이 달라서 태스크를 나눴고, 세 번째 태스크를 둘 이유는 없다. 버튼과 타이머는 태스크가 아니며 큐에 이벤트를 넣기만 한다.

```c
typedef enum { EV_A, EV_B, EV_TICK } event_t;
typedef enum { RUN, PAUSE } state_t;

void vLogicTask(void *p) {
    state_t s = PAUSE; uint32_t count = 0; event_t ev;
    for (;;) {
        xQueueReceive(q, &ev, portMAX_DELAY);   /* 이 지점에서만 대기 */
        switch (s) {
        case RUN:
            if (ev == EV_A) s = PAUSE;
            else if (ev == EV_B) count = 0;
            else if (ev == EV_TICK) count++;
            break;
        case PAUSE:
            if (ev == EV_A) s = RUN;
            else if (ev == EV_B) count = 0;
            break;                              /* TICK은 무시 */
        }
        g_display_value = count;
    }
}
```

상태 전이표의 칸 하나가 `if` 문 하나에 대응한다. 표에 없는 조합은 코드에도 없다. 디버깅할 때는 현재 상태와 태스크가 받은 이벤트, 두 가지만 확인하면 된다.

## 제품 펌웨어에 적용

내가 맡은 MFC 펌웨어에도 경로가 두 가지 있다.

- 빠른 데이터 경로: 센서 입력, 제어 연산, 밸브 구동 출력. 입력이 출력을 바로 정하는 함수 구조이며, 주기 태스크 하나나 타이머 ISR이 실행한다.
- 느린 명령 경로: 명령, 모드 전환, 오류 처리. 상태 머신 구조이며, 로직 태스크 하나가 큐 하나로 이벤트를 받아 처리한다.

처음에 생각한 ‘장치는 함수’라는 관점은 빠른 경로에만 맞는다. 느린 경로를 빠른 경로처럼 다뤄서 버튼 문제를 풀지 못했다.

## 요약

- 태스크는 기능별로 나누지 않고, 기다리는 대상(이벤트 또는 주기)별로 나눈다.
- 이벤트를 처리하는 로직은 상태 전이표를 먼저 쓰고 나서 코드를 작성한다.

다음에는 같은 사양을 슈퍼루프, FreeRTOS, 모든 이벤트를 `tick()` 함수 하나에서 처리하는 동기식 설계로 각각 구현하고, 하드웨어 없이 PC에서 테스트하기가 얼마나 쉬운지 비교한다.
