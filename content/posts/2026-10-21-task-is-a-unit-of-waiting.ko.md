FreeRTOS 태스크는 기능별로 분리하지 않고, 각 태스크의 대기 대상을 기준으로 분리합니다. 이 기준은 버튼 2개로 동작하는 카운터를 구현하는 과정에서 정리하였습니다.

## 1. 문제

과제는 7세그먼트 디스플레이 카운터 구현이며, 사양은 다음과 같습니다.

- 버튼 A: 카운트 시작(1초마다 1씩 증가). 다시 누르면 일시 정지, 한 번 더 누르면 이어서 카운트
- 버튼 B: 상태와 관계없이 카운트를 0으로 초기화
- 일시 정지 중 B 입력 시 0을 표시하고 일시 정지 유지. 동작 중 B 입력 시 0부터 다시 카운트

태스크는 2개로 구성하였습니다. 디스플레이 태스크는 공유 변수의 값을 표시하고, 카운터 태스크는 1초마다 이 값에 1을 더합니다. 이 단계까지는 정상 동작하였습니다.

그러나 버튼 B를 처리할 위치는 정하지 못하였습니다. B의 동작이 상황에 따라 다른 것처럼 보여, 어느 함수에서 처리해야 하는지 판단할 수 없었습니다. MCU 펌웨어 개발 경력이 2년이었지만 처음에는 해결 방법을 찾지 못하였습니다.

## 2. 원인

입력에 따라 출력이 정해지는 함수로 장치를 보았기 때문입니다. 현재 개발 중인 제품이 이 구조로, 제어 루프에서 ADC 값을 읽고 연산한 뒤 DAC로 출력합니다.

카운터는 같은 입력(B)이라도 이전에 발생한 일에 따라 결과가 달라집니다. 디지털 논리로 보면 카운터는 순차 논리이고 함수는 조합 논리입니다. 함수에는 이전 상태를 기억하는 요소가 없으므로 카운터를 표현할 수 없습니다.

기존 관점에 없던 개념은 상태이며, 상태를 포함하면 장치는 다음과 같이 표현됩니다.

> 출력 = f(입력, 상태), 다음 상태 = g(입력, 상태)

상태는 RUN과 PAUSE 2개, 이벤트는 A, B, TICK 3개이며, 상태 전이표는 다음과 같습니다.

<표 1> 카운터 상태 전이표

| 상태 \ 이벤트 | A | B | TICK |
|---|---|---|---|
| RUN | PAUSE로 전이 | count = 0 | count++ |
| PAUSE | RUN으로 전이 | count = 0 | (무시) |

표로 정리하면 B의 동작은 단순합니다. B는 두 상태에서 모두 카운트를 0으로 설정하고 상태는 변경하지 않습니다. RUN 상태에서 카운트가 0부터 다시 증가하는 것은 RUN 상태가 TICK 이벤트를 계속 처리하기 때문이며, B의 동작과는 무관합니다.

## 3. 태스크 분리 기준

처음에는 디스플레이, 카운터, 버튼 등 기능별로 태스크를 하나씩 구성하려 하였으나, 이는 잘못된 기준이었습니다.

FreeRTOS의 태스크는 고유한 스택이 있는 실행 단위이며, CPU를 사용하지 않고 대기(블로킹)할 수 있습니다. 대기할 대상이 없는 작업은 별도 태스크가 필요하지 않고 함수 호출로 충분합니다. 따라서 현재는 대기 대상을 기준으로 태스크를 다음과 같이 분리합니다.

- 같은 주기에 정해진 순서로 실행하는 작업: 한 태스크로 구성
- 주기가 다르거나 다른 이벤트를 대기하는 작업: 별도 태스크로 분리
- 주변장치: 분리 기준에서 제외. 해당 주변장치가 필요한 태스크에서 사용
- 인터럽트 서비스 루틴(ISR): 이벤트를 큐에 넣고 즉시 반환

태스크는 그대로 2개입니다. 로직 태스크는 이벤트를, 디스플레이 태스크는 2&nbsp;ms 주기를 대기합니다. 대기 대상이 서로 다르므로 두 태스크로 분리하며, 세 번째 태스크는 필요하지 않습니다. 버튼과 타이머는 태스크로 구성하지 않고 큐에 이벤트를 넣는 역할만 합니다.

```c
typedef enum { EV_A, EV_B, EV_TICK } event_t;
typedef enum { RUN, PAUSE } state_t;

void vLogicTask(void *p) {
    state_t s = PAUSE; uint32_t count = 0; event_t ev;
    for (;;) {
        xQueueReceive(q, &ev, portMAX_DELAY);   /* 유일한 대기 지점 */
        switch (s) {
        case RUN:
            if (ev == EV_A) s = PAUSE;
            else if (ev == EV_B) count = 0;
            else if (ev == EV_TICK) count++;
            break;
        case PAUSE:
            if (ev == EV_A) s = RUN;
            else if (ev == EV_B) count = 0;
            break;                              /* TICK 무시 */
        }
        g_display_value = count;
    }
}
```

상태 전이표의 각 칸은 `if` 문 하나에 대응하며, 표에 없는 조합은 코드에도 없습니다. 디버깅 시에는 현재 상태와 수신한 이벤트 2가지만 확인하면 됩니다.

## 4. 제품 적용

현재 개발 중인 제품도 다음과 같이 2개 경로로 구분됩니다.

- 빠른 데이터 경로(센서 입력, 제어 연산, 액추에이터 출력): 함수 구조. 주기 태스크 1개 또는 타이머 ISR에서 실행
- 느린 제어 경로(명령, 모드 전환, 오류 처리): 상태 기계 구조. 큐 1개와 로직 태스크 1개에서 실행

‘장치는 함수’라는 처음 관점은 빠른 경로에만 해당합니다. 버튼 문제를 해결하지 못한 원인은 느린 경로를 빠른 경로와 같은 방식으로 다룬 데 있습니다.

## 5. 요약

- 태스크는 기능이 아닌 대기 대상(이벤트 또는 주기)을 기준으로 분리
- 이벤트를 처리하는 로직은 상태 전이표를 먼저 작성한 후 코드로 구현

다음 글에서는 같은 설계를 슈퍼루프, FreeRTOS, 동기식 설계(모든 이벤트를 `tick()` 함수 하나에서 처리) 3가지 방식으로 구현합니다. 이후 하드웨어 없이 PC에서 각 방식을 얼마나 쉽게 시험할 수 있는지 비교하겠습니다.
