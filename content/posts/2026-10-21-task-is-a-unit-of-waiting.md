## 막혔던 문제

7세그먼트 디스플레이에 숫자를 띄우는 작은 연습을 했다. 사양은 이렇다.

- 버튼 A: 누르면 카운트 시작(1초에 1씩 증가). 다시 누르면 일시정지. 다시 누르면 재개.
- 버튼 B: 누르면 항상 0으로 초기화.
- 단, 일시정지 중에 B를 누르면 0에서 멈춰 있고, 실행 중에 B를 누르면 0부터 다시 올라간다.

태스크는 두 개로 나눴다. 디스플레이 태스크는 전역 변수의 숫자를 그냥 그린다. 카운터 태스크는 1초마다 숫자를 올린다. 여기까지는 됐다.

그런데 버튼 B를 어디에 넣어야 할지 애매했다. "B는 상황에 따라 다르게 동작하는 것"처럼 보였고, 그걸 어떤 함수로 써야 하는지 한참 헤맸다. MCU 펌웨어를 2년 짰는데도 그랬다.

## 왜 막혔나

펌웨어 장치를 **입력이 들어오면 출력이 나오는 함수**로 생각하고 있었다. ADC로 읽고, 계산하고, DAC로 쓴다. 지금 만드는 제품의 제어 루프가 실제로 그렇게 생겼으니까.

그런데 버튼 예제는 함수가 아니다. 같은 입력(B)이 들어와도 **과거에 따라 결과가 다르다.** 전자공학으로 말하면 조합논리가 아니라 순차논리다. 함수 틀에 안 들어가는 걸 함수로 보려고 하니 안 보였던 거다.

빠진 단어는 하나였다. **상태.**

> 출력 = f(입력, 상태), 다음 상태 = g(입력, 상태)

상태를 명시하자 문제가 표 하나로 줄었다. 상태는 RUN/PAUSE 둘, 사건은 A, B, TICK 셋.

| 상태 \ 사건 | A | B | TICK |
|---|---|---|---|
| **RUN** | → PAUSE | count = 0 | count++ |
| **PAUSE** | → RUN | count = 0 | (무시) |

그리고 이 표를 보는 순간 알았다. B는 "상황에 따라 다르게 동작하는 것"이 아니었다. **두 상태에서 똑같이 `count = 0`만 한다.** "실행 중이면 다시 올라간다"는 B의 성질이 아니라, RUN 상태가 TICK을 계속 받는다는 성질이다. 내 머릿속에서 B를 복잡하게 모델링했을 뿐, 표에서는 가장 단순한 사건이었다.

## 그럼 태스크는 뭔가

태스크를 기능 단위로 나누고 있었다. "디스플레이 담당", "카운터 담당", 그리고 "버튼 담당?"

틀린 기준이었다. 기술적으로 태스크는 **자기 스택을 가져서 블록할 수 있는 실행 흐름**이다. 블록할 수 없다면 태스크일 이유가 없다. 함수 호출이면 된다. 그러니까 태스크를 나누는 기준은 기능도, 주변장치도 아니고 **무엇을 기다리느냐**다.

- 같은 주기로, 같은 순서로 일어나야 하는 일 → 한 태스크
- 주기가 다르거나, 다른 사건을 기다리는 일 → 다른 태스크
- 주변장치는 태스크가 아니다. 필요한 태스크가 가져다 쓴다
- ISR은 사건을 큐에 넣고 바로 나간다

태스크는 여전히 둘이다. 로직 태스크는 **사건**을 기다리고, 디스플레이 태스크는 **2ms**를 기다린다. 기다리는 게 다르니까 둘이고, 셋일 이유는 없다. 버튼과 타이머는 태스크가 아니라 사건의 공급자다.

```c
typedef enum { EV_A, EV_B, EV_TICK } event_t;
typedef enum { RUN, PAUSE } state_t;

void vLogicTask(void *p) {
    state_t s = PAUSE; uint32_t count = 0; event_t ev;
    for (;;) {
        xQueueReceive(q, &ev, portMAX_DELAY);   /* 유일한 기다림 */
        switch (s) {
        case RUN:
            if (ev == EV_A) s = PAUSE;
            else if (ev == EV_B) count = 0;
            else if (ev == EV_TICK) count++;
            break;
        case PAUSE:
            if (ev == EV_A) s = RUN;
            else if (ev == EV_B) count = 0;
            break;                              /* TICK은 무시 */
        }
        g_display_value = count;
    }
}
```

표의 빈칸 하나가 `if` 한 줄이다. 표에 없는 조합은 코드에도 없다. 디버깅할 때 찍을 것은 "지금 상태"와 "들어온 사건" 둘뿐이다.

## 지금 하는 일로 돌아와서

내가 만드는 제품도 결국 두 경로다.

- **빠른 주기 데이터 경로** — 센서 읽기 → 제어식 → 액추에이터. 이건 함수다. 주기 태스크 하나, 또는 타이머 ISR.
- **느린 사건 제어 경로** — 명령 수신, 모드 전환, 오류 처리. 이건 상태기계다. 큐 하나, 로직 태스크 하나.

"장치는 함수 같은 것 아닌가"라는 내 직감은 첫 번째 경로만 보고 전체를 설명하려 한 것이었고, 버튼에서 막힌 건 두 번째 경로가 함수 틀에 안 들어가서였다. 둘은 다른 도구다. 함수에는 주기 태스크를, 사건에는 상태기계를.

## 한 줄

태스크는 코드가 사는 곳이 아니라, **기다림이 일어나는 장소**다. "어떻게 나누지"라는 질문은 "무엇을 기다리지"와 "상태가 몇 개지"라는 두 개의 작은 질문으로 바뀐다.

다음 글에서는 이 설계를 슈퍼루프, FreeRTOS, 동기식(모든 사건을 `tick()` 하나가 처리) 세 가지로 구현하고, 어느 것이 하드웨어 없이 PC에서 테스트되는지 비교해 볼 생각이다.
